Free check · runs in your browser

Check what your AI agent actually resolved.

Drop two exports: your AI agent's conversations and your tickets. In about a minute you'll see how many conversations it marked resolved came back as a ticket within a week, next to your agents' own resolutions. Nothing is uploaded.

Nothing leaves your machine. The check runs inside this page: it reads your files in your browser and never sends them anywhere. The page's security policy backs that up: it blocks the ways a script sends data (fetch, uploads, beacons, sockets and form posts) and stops the page loading anything from another site. For proof you can see, turn off your Wi-Fi once this page has loaded and run the check: it works the same. Or download the check as one file and run it offline. The code is open: read it.

Not ready to export yet?

Before you export: check your company's rules for putting incident data on your laptop, and use Sys IDs to keep names out of the files. If your security team needs to sign off, send them the note for security teams.

The steps below are for ServiceNow. On Zendesk, Jira Service Management, Freshservice, BMC Helix, Ivanti or any other tool, export the same fields as CSV. For the conversations, include the column that says how each one ended, and list the values that mean resolved under Options.

1. Virtual Agent conversations

In ServiceNow, open interaction.list, filter to Virtual agent = true for the months you want, and export as CSV with: Number, Opened for, Opened, State, State reason, Agent chat, Type.

2. Incidents for the same months, plus a week

Export incident.list as CSV with: Number, Caller, Opened, Resolved, Contact type, Reopen count, and Category for the fix list. Contact type lets the check tell incidents the virtual agent opened itself from people coming back; Reopen count shows how often your agents' fixes didn't hold. Use the same kind of person field as the conversations: both names, or both Sys IDs.

Questions

Is this the full audit?

No. It's a screening estimate: it uses the same definitions as the open engine's resolution audit and gives the same rates on the same files, but a return is any ticket from the same person, and the comparison is with all of your agents' resolutions. The full audit also matches the type of issue, runs more checks and widens the range with a month-by-month check. Run it with pip install probative-labs, or book a call and I'll run it with you.

What counts as "came back"?

The same person opened an incident within the window after the conversation started. Some people come back after any help, so the same check runs on incidents your agents resolved in the same months, and only the excess counts as "did not hold".

An incident the virtual agent opened itself doesn't count. ServiceNow's Create Incident topic sets Contact type to Virtual Agent, so an incident through that channel within 30 minutes of the person's conversation came from it: that conversation was a handoff, and it's left out. Without Contact type, incidents opened in the first 30 minutes after a conversation or a resolution don't count on either side, and the result shows what changes if they do.

Do people who call or walk up count?

Yes, when your team logs an incident for them: any incident from the same person counts, whatever its channel. Contacts nobody logs can't be seen. That's true after your agents' resolutions too, which is why the two are compared rather than read on their own.

What about catalog requests?

Requests aren't incidents. A topic that submits a request isn't counted as a failure, and a request opened after a chat isn't counted as a return.

What if ServiceNow disputes the number?

Then it can rerun it. The definitions come from ServiceNow's own fields (State, State reason, Agent chat, Contact type), every step is in open code, and anyone can rerun the numbers on the same exports. The result also shows how much it depends on each choice, so a challenge has to be about the data, not the method.

What exactly does the security policy block?

Everything except this site's own script, stylesheet and images (default-src 'none'). Scripts can't fetch, upload, open sockets or send beacons (connect-src 'none'), forms can't post (form-action 'none'), and nothing loads from another site. No policy can stop a page from navigating away, which is why the code is open and why the offline test is the real proof. The downloaded copy is stricter still: it can run only the code inside the file.

Can I share the result?

Download the summary: rates and counts only, with no names, IDs or ticket contents. Send that, not the exports, if you'd like a second opinion.

Our AI agent isn't ServiceNow.

Any export with a person, a start time and an outcome works. Drop the files, check the matched columns, and under Options list the outcome values that mean resolved. For Intercom, export conversations with the Fin AI Agent resolution state and list Assumed resolution, Confirmed resolution. Ticket exports from Zendesk, Jira Service Management, Freshservice, BMC Helix and Ivanti are matched automatically. Those column names come from each vendor's documentation and haven't been tested on a customer's real export yet, so check the matched columns before you run it.
